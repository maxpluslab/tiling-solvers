# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A solver laboratory for geometric tiling puzzles: shared Rust geometry, interchangeable solvers behind one `solve()` contract, independent validation, and benchmarking. The design is in `docs/architecture.md`; the algorithmic background and literature are in the research brief, `docs/research-brief.md`, and where they differ the architecture document decides. Work proceeds one phase at a time from `docs/roadmap.md`; read the phase before starting it and tick it off when its exit criterion is met. Everything committed here is public.

The puzzles come from the sibling repository `maxpluslab/tropical-puzzle-lab` (usually cloned at `../tropical-puzzle-lab`). Its `docs/puzzle-format.md` and `docs/puzzle-rules.md` define the source format and the completion rules, and `web/src/geometry/evaluate.ts` is the reference implementation of those rules. The puzzle generator stays there; never move it here.

## Commands

```sh
uv sync                                   # create .venv, build the Rust extension
uv run pytest                             # all Python tests
uv run pytest tests/unit/test_native.py::test_version_matches_the_package
uv run pytest tests/corpus                # every committed fixture and its answer key
uv run pytest tests/corpus/test_native_agrees_with_validator.py   # Rust geometry against the validator
uv run pytest -m "not source"             # without the tropical-puzzle-lab checkout
HYPOTHESIS_PROFILE=ci uv run pytest       # the derandomized, larger property runs CI uses
uv run ruff check && uv run ruff format --check
uv run pyright

cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --exclude tiling-py          # tiling-py is a cdylib, tested through pytest
cargo test -p tiling-geometry signed_area

uv run maxplus-solve new5-flat --max-solutions all --validate                     # run a solver from the command line
uv run python scripts/import_fixtures.py --source ../tropical-puzzle-lab          # regenerate fixtures and keys
uv run python scripts/import_fixtures.py --source ../tropical-puzzle-lab --check  # compare, write nothing
```

`uv sync` and `uv run` rebuild the extension when anything under `crates/` changes (`[tool.uv] cache-keys` in `pyproject.toml`). The extension uses the stable ABI (`abi3-py311`), so one build serves every supported Python. CI (`.github/workflows/ci.yml`) runs all of the above on Linux and Windows. It checks out tropical-puzzle-lab at the commit recorded in `benchmarks/fixtures/index.json`, so the `source` tests always run there.

## Architecture

- `crates/tiling-core`: domain types. No dependencies on the other crates.
- `crates/tiling-geometry`: convex geometry, contact matching, candidate generation. Depends on core. Primitives take `&[Vec2]`; proptest strategies shared by its tests are in `src/testing.rs`.
- `crates/tiling-search`: custom solvers, one module each. Depends on core and geometry.
- `crates/tiling-py`: PyO3 bindings, built by maturin as `maxplus_solvers._native`. Converts types and forwards calls; no algorithms.
- `python/maxplus_solvers`: the user-facing package: models, importers, solver adapters, validation, experiments. When a function is added to `_native`, add it to `_native.pyi` too. `_native` takes a polygon as a sequence of pairs, a pose as `(x, y, theta)` and a roof as `(z0, gx, gy)`.
  - `models.py` holds the contracts; `schemas/instance-v1.json` is their JSON form and `tiling-core` mirrors the instance types. Change all three together.
  - `sanitize.py` is the only way an answer-bearing puzzle becomes an instance. `io/tropical.py` and `synthetic.py` both go through it.
  - `api.py` holds `load_puzzle` and `solve`; `solvers/` holds the registry and one module per solver, prototypes under `solvers/prototypes/`. `docs/solver-contract.md` says what a result claims and `docs/algorithms.md` why each search rule is sound; a solver change updates both.
  - `validation.py` is the completion check, on Shapely (the `validate` extra). Importing the package must not load Shapely; only this module does.
- `benchmarks/fixtures/` and `tests/keys/` are generated by `scripts/import_fixtures.py`. Never edit them by hand: change the importer or the source and regenerate.

## Testing

The test suite is part of the product. This is a research platform, and a result is only as good as the checks behind it.

A phase is ticked off in the roadmap only when its exit criterion is an automated test that passes in CI on both platforms. Passing on one machine is not an exit.

Where tests go:

| Directory | Contents |
| --- | --- |
| `tests/unit/` | One behaviour per test, on small inputs whose expected values can be worked out by hand. |
| `tests/property/` | Hypothesis suites over random polygons, poses and seeds. Rust properties use proptest, beside the code. |
| `tests/corpus/` | Parametrized over every committed fixture and its answer key. Phase exit criteria live here. |
| `tests/architecture/` | The invariants below, checked mechanically: layering, stub drift, optional dependencies, who may read answers. |
| `tests/support/` | Shared helpers: the oracle (`geometry.py`), Hypothesis strategies, loaders, hand-written documents. |

Rules:

- **Expected values come from somewhere else.** Work them out by hand and say how in a comment, or use `tests/support/geometry.py`, the Shapely validator, or the answer keys. A test that computes its expectation with the code under test checks nothing. Pinned regression values are allowed only where no oracle exists (seeded randomness) and must be labelled as such.
- **Every check has a test that makes it fail.** A validator rule, a schema constraint or a leak guard is not done until a deliberately broken input is refused. When adding a guard, break the thing by hand once and watch the test go red.
- **New geometry gets a property test,** in proptest for Rust and Hypothesis for Python. Rust geometry that reaches `_native` is also tested differentially against Shapely or the validator, in `tests/property/test_native_properties.py` and `tests/corpus/test_native_agrees_with_validator.py`: lengths to 1e-9 mm, areas to 1e-6 mm².
- **Every numeric comparison states its tolerance:** `pytest.approx(x, abs=1e-9)`, never a bare `approx` or `==` on computed floats.
- **Tests are deterministic.** Randomness is seeded; nothing asserts on wall-clock time. The Hypothesis `ci` profile is derandomized so a CI failure reproduces locally.
- **Nothing is skipped in CI.** Warnings are errors, `xfail` is strict, and unknown markers are rejected. Only `source`-marked tests may skip, and only on a machine without the tropical-puzzle-lab checkout; in CI a missing checkout is a failure.
- **Unit and property tests need no other repository.** Importer tests use the hand-made `tests/data/source/mini`. Only tests marked `source` read tropical-puzzle-lab.
- **A bug fix starts with a test that fails.**
- **When an invariant is added to this file, add its test to `tests/architecture/`** if it can be checked mechanically.

## Invariants that are easy to break

- **Solver instances carry no answer.** The source `puzzle.json` leaks the solution three ways: `reference.poses`; local polygons stored in their solved orientation (every reference `theta` is 0); and piece ids and order that encode the tropical construction. Instances must be sanitized: seeded random rotation per piece (roof gradient rotated with it), random starting vertex, shuffled order, opaque ids, no `reference`, `tropical` or `provenance`. The sanitizer seed is part of the answer, since the rotations can be recomputed from it: it is recorded in the answer key and never in an instance. Answer keys live under `tests/` and only tests load them.
- **Three information regimes stay separate:** footprint (polygons only), relief (polygons and roof planes), tropical-aware (construction data as well). A solver declares which one it uses; results from different regimes are not comparable.
- **The validator is independent of the search.** `validation.py` must not import `_native` or reuse the Rust geometry, so one bug cannot affect both. It follows the browser's completion rules and may only depart from them on the stricter side; the three places it does are listed in its module docstring.
- **Solvers never call the validator.** `api.solve(..., validate=True)` is the only place the two meet, after the search has returned. A search that consulted the validator would be checking its answer with its own oracle.
- **Completeness and uniqueness are explicit claims.** A result says whether the search was exhaustive and over which candidate set. "No solution found" and CP-SAT `INFEASIBLE` are relative to the candidates generated unless completeness is proven.
- **Layering is one-way:** core ← geometry ← search ← py. Python reaches Rust only through `_native`.
- **Production solvers cross the Python/Rust boundary once per solve.** Prototypes may call individual geometry primitives; a Rust solver receives the instance and runs to completion.
- **Units are millimetres and radians,** matching the browser player. Polygons are convex and counter-clockwise, in local coordinates about the area centroid. A pose rotates by `theta` then translates by `(x, y)`.
- **`f64` with explicit tolerances is not exactness.** Don't describe a floating-point result as a mathematical proof.
- **Optional dependencies stay optional.** OR-Tools, Shapely and the analysis stack are extras; the Rust solvers must run without them.
